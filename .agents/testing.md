# 测试说明

## 何时更新
- 当测试命令、测试框架、测试目录结构或覆盖策略发生变化时，必须更新本文件。
- 当某个子项目新增稳定测试入口或移除测试能力时，必须更新本文件。

## 测试目标
- 修改代码后，必须优先验证受影响模块，再决定是否运行更大范围的测试。
- 如果改动改变了已有逻辑、修复了缺陷或新增了行为，并且对应目录已经存在测试体系，则必须新增或更新测试。
- 如果对应目录没有测试体系，不要擅自引入新的测试框架，除非用户明确要求。

## 执行顺序
1. 先定位本次改动影响的模块和目录。
2. 先运行最相关的测试。
3. 如果已有稳定全量测试命令，再运行全量测试。
4. 如果测试暴露的是本次改动引入的问题，必须继续修复并重新验证。
5. 如果测试无法运行，必须在最终回复中说明未运行项和原因。

## 根目录
- 当前没有统一的全仓测试命令。
- 根目录 `package.json` 仅提供开发和前端构建命令，不负责统一测试。

## 后端
- 目录：`backend/`
- 现有测试框架：`vitest`
- 全量测试命令：`cd backend && npm test`
- 监听模式：`cd backend && npm run test:watch`
- 覆盖率命令：`cd backend && npm run test:coverage`
- 规则：后端逻辑、路由、服务层、数据库适配层发生变化时，优先补充或更新后端测试。

## 前端
- 目录：`frontend/`
- 现有测试框架：`vitest`
- 全量测试命令：`cd frontend && npm test`
- 监听模式：`cd frontend && npm run test:watch`
- 覆盖率命令：`cd frontend && npm run test:coverage`
- 规则：前端视图、组件、状态流转、接口消费逻辑发生变化时，优先补充或更新前端测试。

## Android
- 目录：`android-native/`
- 建议测试命令：`cd android-native && .\\gradlew test`
- 说明：当前仓库可通过 Gradle 运行单元测试，但是否已存在完整测试集需要按目录实际情况判断。
- 规则：只有在现有 Android 测试目录和测试依赖已具备时，才自动补充 Android 测试。

## 文档联动规则
- 改动影响功能行为时，同时更新 `features.md`。
- 改动影响数据流、模块职责或存储策略时，同时更新 `architecture.md`。
- 改动影响本地启动、环境变量、测试命令时，同时更新 `setup.md` 或本文件。
- 改动影响部署流程、生产环境变量或云端配置时，同时更新 `deploy.md`。
